# OHOS development from the fork

Use the `ohos` branch of `richerfu/nsh` for OHOS development. Build the host CLI and the OHOS embedding SDK
from the same checkout and lockfile, then use that CLI to produce the app's bundles and editor declarations.
This keeps the compiler, native exports and embedded runtime together as the fork tracks upstream changes.
The package version alone does not identify the fork: `nsh --version` also prints its source revision.

This guide covers source selection, replacing an installed CLI, SDK assembly and dependency overrides.
See [ohos.md](ohos.md) for the backend architecture, [embedding.md](embedding.md) for embedding concepts, and
[the embedding example](../../examples/embed-ohos/README.md) for the host channel and native component sample.

## Which parts come from where

| Part | Source for this workflow | How it reaches the app |
|---|---|---|
| `nsh` CLI (`nsh-cli`, bundler, declarations and bytecode compiler) | `richerfu/nsh`, branch `ohos` | Build on the development machine; select its executable explicitly |
| `libnsh_platform_ohos.so` (core, engine, QuickJS and ArkUI backend) | The same checkout and `Cargo.lock` | `cargo xtask ohos`, then copy into the HAP |
| `@nsh/ohos` and the native library's `index.d.ts` | The same SDK build | Copy the complete staged package and declarations with the library |
| TSX app declarations (`.nsh/types`, `.nsh/tsconfig.json`) | The selected fork CLI | Regenerated by `nsh build`, `nsh check` and `nsh dev` |
| `ohos-*` Rust bindings, `napi-*-ohos`, QuickJS | Registry dependencies recorded in `Cargo.lock` | Cargo resolves them while building the CLI and SDK |
| `libc++_shared.so`, OHPM, Hvigor and signing tools | The selected DevEco / OpenHarmony SDK | Assemble, sign and install the host app |

The current branch uses released OHOS bindings. The earlier local `ohos-native-bindings` patch described in
[audit item P0-6](ohos-audit.md#p0-6--the-branch-needs-an-unreleased-ohos-arkui-binding-wrapper) is historical;
its resolution removed the need for that patch. A normal setup needs only this NSH fork and the SDK.

## Check out the OHOS source

For a new checkout:

```sh
git clone --branch ohos https://github.com/richerfu/nsh.git nsh-ohos
cd nsh-ohos
git status --short --branch
git rev-parse HEAD
```

In an existing fork checkout, fetch `origin`, preserve any local changes, and switch to its `ohos` branch.
Check `git remote -v`: in this workflow `origin` is `richerfu/nsh`; `longbridge/nsh` is the upstream source.
If an older checkout has local `ohos/*` branches, Git cannot also create a branch named `ohos`. Rename the
old local branches to an archive namespace first. `git fetch --prune origin` removes obsolete remote-tracking
names after the corresponding remote branches have been removed.

The commands below run from the fork's root. They use macOS shell paths for the embedding example;
the Rust SDK build also supports Linux and Windows. Rust/Cargo follow the repository's
[development setup](../../AGENTS.md#commands). The Cargo fork named there is a build tool;
selecting it does not select NSH's source branch.

## Build and select the fork CLI

The CLI runs on the development machine. Build it for that machine, then point tools at its executable:

```sh
cargo build --locked --release -p nsh-cli
export NSH_CHECKOUT="$PWD"
export NSH_CLI="$NSH_CHECKOUT/target/release/nsh"
"$NSH_CLI" --version
git rev-parse --short=7 HEAD
```

The revision in `--version` should match this checkout's HEAD after the build. Uncommitted changes are not
identified by that revision, so record `git status --short` when sharing a build. These paths use Cargo's
usual `target/` layout. If an existing Cargo configuration places the CLI elsewhere, set `NSH_CLI` to the
actual executable; `cargo metadata --no-deps --format-version 1` reports `target_directory`.

Use `"$NSH_CLI"` in scripts. To replace the `nsh` command for the current shell as well:

```sh
export PATH="$NSH_CHECKOUT/target/release:$PATH"
hash -r
type -a nsh
nsh --version
```

Check for an alias or shell function if `type -a nsh` still resolves another command. The absolute
`NSH_CLI` path makes the build script independent of shell aliases and other installations. Keep the CLI
in its checkout, so rebuilding after a source update replaces the executable that the app uses.

`NSH_CLI` is read by `examples/embed-ohos/build.sh`; setting it alone does not redirect a bare `nsh` command.
Homebrew, `cargo install nsh-cli` without a source override, and the standard NSH installer select the
published/upstream CLI. In this checkout, `website/public/install.sh --source` explicitly fetches
`longbridge/nsh`'s `main`; `NSH_VERSION` selects a release, not the fork's branch. Maintain the OHOS CLI by
updating and rebuilding this checkout. `NSH_RUNTIME` selects prebuilt runtimes for the CLI's supported hosts;
it does not select the fork or the OHOS SDK consumed by the example.

## Build the matching OHOS SDK

Install the OHOS Rust target explicitly; the repository's `rust-toolchain.toml` lists the other mobile
targets. Select an API 20+ SDK, and use a device or emulator with the API level required by the build.
For the macOS example script, set both paths below to the DevEco installation you use:

```sh
rustup target add aarch64-unknown-linux-ohos
export DEVECO_CONTENTS="/Applications/DevEco-Studio.app/Contents"
export OHOS_NDK_HOME="$DEVECO_CONTENTS/sdk/default/openharmony"
cargo xtask ohos --release
```

`OHOS_NDK_HOME` here is the `openharmony` directory containing `native/`. `xtask` discovers SDKs on all
three host systems and configures the NDK compiler, linker, archiver, sysroot and bindgen arguments.
Use it for the cross-build; the CLI itself stays a host executable.

| SDK command | `NSH_PROFILE` for the example | Minimum API |
|---|---|---|
| `cargo xtask ohos` | `debug` | 20 |
| `cargo xtask ohos --dev` | `debug-dev` | 20 |
| `cargo xtask ohos --release` | `release` | 20 |
| `cargo xtask ohos --release --dev` | `release-dev` | 20 |
| `cargo xtask ohos --release --features api-23` | `release-api-23` | 23 |
| `cargo xtask ohos --release --dev --features api-26` | `release-dev-api-26` | 26 |

`--dev` enables the dev-server client; the higher API features enable the enhancements described in
[ohos.md](ohos.md#building-and-checking). A higher API build also needs the host app's compatible SDK
version and target device aligned with that minimum. The checked-in example targets API 20.

Each build writes a complete SDK under `target/ohos/<profile>/`:

```text
arm64-v8a/libnsh_platform_ohos.so
index.d.ts
arkts-deps/nsh/
build-metadata.json
```

Keep these files together. `build-metadata.json` records the minimum API, features, binding source,
Git binding revision when applicable, library/declaration hashes and whether path development was enabled.
It does not record the NSH checkout revision; retain `git rev-parse HEAD` with the build record too.
`cargo xtask dist` assembles the other platform distributions; this workflow stages OHOS with `xtask ohos`.

## Assemble and run the embedding example

After building the release CLI and release SDK above:

```sh
NSH_PROFILE=release NSH_CLI="$NSH_CLI" examples/embed-ohos/build.sh
```

The script performs the replacements as one sequence:

1. Copies `target/ohos/$NSH_PROFILE/arkts-deps/nsh/` into `target/ohos/arkts-deps/nsh/`.
   The example's `build-profile.json5` and `entry/oh-package.json5` reference this fixed staging path.
2. Copies that profile's `libnsh_platform_ohos.so` into `entry/libs/arm64-v8a/`, its `index.d.ts` into
   `entry/src/main/cpp/types/libnsh_platform_ohos/Index.d.ts`, and the NDK's `libc++_shared.so` alongside the library.
3. Invokes the selected CLI to build the TSX app into `entry/src/main/resources/rawfile/`, including split
   chunks by default, then runs DevEco's OHPM and Hvigor to assemble a debug HAP.

The script's controls are independent:

| Variable | Default | What it selects |
|---|---|---|
| `NSH_CLI` | `<checkout>/target/debug/nsh` | Host CLI executable; use an absolute path |
| `NSH_PROFILE` | `debug` | Complete SDK directory under `target/ohos/` |
| `NSH_EXAMPLE` | `examples/embedded` | TSX app path relative to the NSH checkout |
| `NSH_SPLIT` | `1` | Pass `--split` when `1`; use `0` for one bundle |

For example, select another app with `NSH_EXAMPLE=examples/counter`. Selecting a release SDK does not
change the script's HAP build mode or add `--release` to `nsh build`. For a minified bundle, use the selected
CLI's `build --release` explicitly in your host's packaging pipeline. The example loads `bundle.js`;
loading `bundle.nshc` requires changing the host's `loadResource` argument and rebuilding the HAP.

Configure local signing in DevEco Studio for `com.example.nsh`, then assemble the signed HAP and install it.
Keep signing certificates, passwords and machine paths local. Select the device ID from `hdc list targets`:

```sh
hdc list targets
export NSH_DEVICE="your-device-id"
hdc -t "$NSH_DEVICE" install -r examples/embed-ohos/entry/build/default/outputs/default/entry-default-signed.hap
hdc -t "$NSH_DEVICE" shell aa start -a EntryAbility -b com.example.nsh
```

For an existing OHOS host, apply the same library, declarations, ArkTS package and rawfile replacements to
its module. Copy the whole bundle output, including `app.json`, `capabilities.json` when present, chunks,
maps and assets. Split bundles need their companion files; copying only the entry leaves imports unresolved.

### Hot reload

Build and select a dev SDK, then replace the example's `surface.loadResource("bundle.js")` with
`surface.connectDevServer("ws://127.0.0.1:8790/ws")` before assembling and installing the host:

```sh
cargo xtask ohos --release --dev
NSH_PROFILE=release-dev NSH_CLI="$NSH_CLI" examples/embed-ohos/build.sh
hdc -t "$NSH_DEVICE" install -r examples/embed-ohos/entry/build/default/outputs/default/entry-default-signed.hap
hdc -t "$NSH_DEVICE" rport tcp:8790 tcp:8790
"$NSH_CLI" dev examples/embedded
```

Keep the dev server running and start the installed host from the device, or run the `aa start` command above
in another terminal. TSX changes reload through that connection.
Rust, ArkTS and native declaration changes require rebuilding the SDK and HAP. The OHOS workflow uses
`nsh build` / `nsh dev` plus an embedding host; the current CLI's `run`, `package` and `test` target enums
do not include `ohos`. Use Hvigor and `hdc` for the native host lifecycle.

## Rust dependencies and temporary binding forks

Replacing the CLI does not rewrite an external Rust app's `Cargo.toml`. For a new mixed app that develops
against this fork, the CLI can create path dependencies explicitly:

```sh
"$NSH_CLI" init ../my-mixed-app --template mixed --nsh-source "$NSH_CHECKOUT"
```

`--nsh-source` applies to `rust` and `mixed` templates. Existing Rust apps must also take their NSH crates
from one checkout, or one pinned Git revision of the fork, with a committed lockfile. The generated
workspaces use that resolved source and patch registry/Git references to share the same NSH types
(`crates/nsh-cli/src/rust_app.rs`). A Git checkout with a different NSH package version can be retargeted
to the running CLI's registry version, so verify both the version and the resolved source.
These generated desktop/mobile runners do not add an OHOS packaging target; custom Rust UI sets must be
integrated into the OHOS host separately.

For the SDK's OHOS bindings, the normal path remains the registry versions in the root `Cargo.toml` and
`Cargo.lock`. If a binding change needs a temporary fork:

- Declare the override in the workspace's Cargo patch configuration and pin its Git commit. Patch the
  binding family consistently, including transitive `ohos-*` dependencies, and update the lockfile deliberately.
- `xtask ohos` reads locked Cargo metadata and requires all `ohos-*` packages except `ohos-enum-derive` to
  share one source. A partial registry/Git/path replacement fails this check; identical version numbers
  do not make different sources interchangeable.
- Local path overrides are for binding development. `NSH_ALLOW_PATH_DEPENDENCIES=1 cargo xtask ohos`
  permits the path source, but still requires one consistent source. The flag does not create patches or
  update the lockfile. Remove the flag and path overrides when producing a reproducible SDK.
- After the binding fix is released, update the registry dependency and lockfile, remove the temporary
  patch, and rebuild the CLI/SDK/app as appropriate. Generated `index.d.ts` comes from the build, never a manual edit.

Inspect the resolved dependencies and SDK record when diagnosing a replacement:

```sh
cargo tree --locked --target aarch64-unknown-linux-ohos -p nsh-platform-ohos
cat target/ohos/release/build-metadata.json
```

## Updating and verifying the complete set

With local work saved, update the fork branch and rebuild in order:

```sh
git fetch origin
git merge --ff-only origin/ohos
cargo build --locked --release -p nsh-cli
cargo xtask ohos --release
"$NSH_CLI" check examples/embedded
NSH_PROFILE=release NSH_CLI="$NSH_CLI" examples/embed-ohos/build.sh
```

Use the dev/profile variant selected for your host throughout, reinstall the HAP, and check both bundle
loading and the host channel. A CLI rebuild alone leaves the installed SDK and HAP at their previous revision.
For backend changes, also run `cargo test -p nsh-platform-ohos`, `cargo xtask clippy-ohos`, and the applicable
[repository checks](../../AGENTS.md#verification-after-changes). Host tests cover pure logic;
`target_env = "ohos"` code needs the cross-build and device verification.

| Symptom | Check |
|---|---|
| `nsh --version` shows the upstream or an old revision | Check `type -a nsh`, `NSH_CLI`, and the rebuilt executable's revision |
| A new export is missing, or bytecode does not load | Rebuild CLI and SDK from the same checkout/lockfile; regenerate app output and replace the installed HAP |
| ArkTS declarations disagree with native methods | Copy the library, generated declarations and complete `@nsh/ohos` package from one SDK profile; rerun OHPM/Hvigor |
| `build.sh` cannot find the CLI or staged package | Its defaults are `target/debug/nsh` and SDK profile `debug`; set both selectors explicitly for release builds |
| `OHOS native packages must share one binding source` | Inspect Cargo patch configuration and the resolved tree for a partial dependency replacement |
| Hot reload does not connect | Check the `-dev` SDK, host's `connectDevServer` call, running fork server and `hdc rport` mapping |
| `--target ohos` is rejected by the CLI | Build bundles with the host CLI and assemble/run the embedding HAP with Hvigor and `hdc` |

The implementation references for this workflow are `crates/xtask/src/ohos.rs`,
`examples/embed-ohos/build.sh`, `crates/nsh-cli/build.rs`, and `crates/nsh-cli/src/rust_app.rs`.
